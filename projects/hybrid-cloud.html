Hybrid Cloud Architecture

An on-premises FortiGate connected to Azure VPN Gateway and AWS Transit Gateway with route-based IPsec, BGP route exchange, strict prefix filtering and centralised PRTG monitoring.

Context & objectives

Lab project. Addressing, ASNs and IPs are lab values (documentation ranges for public IPs). Pre-shared keys are redacted.

Most companies end up with workloads in more than one cloud. The goal of this lab was to connect one on-premises site to Azure and AWS at the same time, the way an enterprise would: encrypted, dynamically routed, filtered and monitored from one place.

  • Route-based IPsec (IKEv2) from a FortiGate to Azure VPN Gateway and AWS Transit Gateway.
  • BGP everywhere: no static routes towards the cloud, new VNets / VPCs appear automatically.
  • Strict filtering: on-prem advertises only its LAN, accepts only the expected cloud prefixes.
  • One monitoring view (PRTG) for tunnels, BGP sessions and end-to-end latency.

Design choices

route-based, not policy-basedTunnels as interfacesRouting decides what goes into a tunnel, so BGP, SD-WAN and firewall policies all work on top of it.
Transit Gateway, not a VGWScales to many VPCsOne VPN attachment serves every VPC attached to the TGW. Propagation fills the TGW route table automatically.
prefix lists in & outNo route leaksWithout filters, the FortiGate could re-advertise AWS routes to Azure and become an unplanned transit between clouds.
MSS clampingNo silent dropsIPsec overhead lowers the usable MTU. TCP MSS is clamped to 1350 on cloud-bound policies to avoid fragmentation issues.

Implementation

Plan addressing & ASNs

Non-overlapping prefixes for on-prem, Azure and AWS; private ASNs per domain (65001, 65515, 64512).

Azure side

VNet with GatewaySubnet, route-based VPN Gateway with BGP, a Local Network Gateway describing the FortiGate, then the connection.

AWS side

Transit Gateway, VPC attachment, Customer Gateway (FortiGate public IP + ASN) and a Site-to-Site VPN attached to the TGW: two tunnels.

FortiGate side

Three IPsec interfaces, three BGP neighbors, prefix lists, firewall policies with MSS clamping.

Monitoring

PRTG sensors for tunnel status, BGP state and ping latency to a test VM in each cloud.

Key configuration

Azure (CLI)

az cli
# Route-based VPN gateway with BGP (ASN 65515)
az network vnet-gateway create -g rg-hybrid -n vgw-hub \
  --vnet vnet-hub --public-ip-addresses pip-vgw \
  --gateway-type Vpn --vpn-type RouteBased --sku VpnGw1 --asn 65515

# The FortiGate, seen from Azure
az network local-gateway create -g rg-hybrid -n lng-onprem \
  --gateway-ip-address 203.0.113.10 --asn 65001 \
  --bgp-peering-address 10.1.255.1 --local-address-prefixes 10.1.255.1/32

az network vpn-connection create -g rg-hybrid -n cn-onprem \
  --vnet-gateway1 vgw-hub --local-gateway2 lng-onprem \
  --shared-key "<redacted>" --enable-bgp

AWS (CLI)

aws cli
aws ec2 create-transit-gateway --options \
  AmazonSideAsn=64512,VpnEcmpSupport=enable,DefaultRouteTablePropagation=enable

aws ec2 create-customer-gateway --type ipsec.1 \
  --public-ip 203.0.113.10 --bgp-asn 65001

aws ec2 create-vpn-connection --type ipsec.1 \
  --customer-gateway-id cgw-0abc --transit-gateway-id tgw-0def \
  --options "TunnelOptions=[{TunnelInsideCidr=169.254.10.0/30},{TunnelInsideCidr=169.254.11.0/30}]"

FortiGate: BGP with filtering

FortiOS 7.4 · FG-HQ
config router prefix-list
    edit "PL-ONPREM-OUT"
        config rule
            edit 1
                set prefix 10.1.0.0 255.255.0.0
            next
        end
    next
    edit "PL-AZURE-IN"
        config rule
            edit 1
                set prefix 10.100.0.0 255.255.0.0
                set le 24
            next
        end
    next
    edit "PL-AWS-IN"
        config rule
            edit 1
                set prefix 10.200.0.0 255.255.0.0
                set le 24
            next
        end
    next
end
config router bgp
    set as 65001
    set router-id 10.1.255.1
    set ebgp-multipath enable
    config neighbor
        edit "10.100.255.30"
            set remote-as 65515
            set ebgp-enforce-multihop enable
            set update-source "lo-bgp"
            set prefix-list-in "PL-AZURE-IN"
            set prefix-list-out "PL-ONPREM-OUT"
        next
        edit "169.254.10.1"
            set remote-as 64512
            set prefix-list-in "PL-AWS-IN"
            set prefix-list-out "PL-ONPREM-OUT"
        next
        edit "169.254.11.1"
            set remote-as 64512
            set prefix-list-in "PL-AWS-IN"
            set prefix-list-out "PL-ONPREM-OUT"
        next
    end
    config network
        edit 1
            set prefix 10.1.0.0 255.255.0.0
        next
    end
end

Azure’s BGP peer address sits inside the GatewaySubnet (here 10.100.255.30), so the FortiGate reaches it through the tunnel with eBGP multihop from a loopback. On AWS, the peers are the .1 addresses of each inside /30, and ebgp-multipath lets both tunnels carry traffic.

Things to watch

  • Azure VPN Gateway creation can take 30+ minutes: start it first.
  • AWS tunnel inside CIDRs must be /30s from 169.254.0.0/16, avoiding the ranges AWS reserves.
  • Overlapping prefixes between sites and clouds break everything. Plan the addressing before the first tunnel.
  • Without inbound prefix lists, a mistake in a cloud route table can reach your LAN.
