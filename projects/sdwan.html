SD-WAN Enterprise Migration

Moved a four-site enterprise from MPLS and static routes to a hub-and-spoke Fortinet SD-WAN: two ISPs per site, IPsec IKEv2 / AES-256 and BGP/OSPF. Validated in EVE-NG before cutover.

Context & objectives

Configurations are sanitised and simplified for publication. Failover times are lab measurements taken in EVE-NG with FortiGate 7.4 VMs.

The company connected its sites with a legacy WAN: MPLS plus static routes. When a link failed, traffic stayed black-holed until the static route was changed, typically 3 to 5 minutes. There was no visibility per application and part of the MPLS traffic was unencrypted.

Objectives

  • Faster, automatic failover between links.
  • Application-aware steering (VoIP, bulk data, business apps).
  • Encrypt all intersite traffic, replacing clear-text MPLS segments.
  • Reduce bandwidth cost by sending bulk traffic over a cheaper second ISP.
  • Central management and logs (FortiManager, FortiAnalyzer).

Architecture

A hub-and-spoke overlay: the HQ FortiGate is the hub, each branch is a spoke with two IPsec tunnels to HQ, one per ISP. BGP runs over each tunnel, so routing follows tunnel health; OSPF carries the routes into each LAN.

Design choices

why hub-and-spokeCentral inspectionAll spoke internet traffic is backhauled through HQ for IPS and application control. One policy point, one log source.
why BGP over IPsecDynamic routing per tunnelA failed tunnel withdraws its routes on its own. No static routes to update, and new sites only need a new neighbor.
why SLA probesPerformance, not just link stateA link can be up but unusable. Probes measure latency, jitter and loss, and steer each application to the link that meets its SLA.
why BFDStable BGP on small linksShort BGP timers caused flaps on 20 Mb/s links. BFD detects failures fast while BGP keeps conservative 10 s / 30 s timers.

Implementation

Audit & baseline

Documented peering, routing policies and latency per site. Root causes: static-route failover and no application-aware steering.

Full replica in EVE-NG

Four FortiGate 7.4 VMs (2 vCPU / 2 GB each) on a 32 GB host. Every rule and failure case was tested here first.

IPsec provisioning

IKEv2, AES-256 / SHA-256, DH group 14 with PFS, DPD. Two route-based tunnels per spoke, BGP on each.

SD-WAN rules & SLA probes

VoIP prefers ISP-1, bulk data goes to ISP-2, business apps take the lowest-latency member.

FortiManager push & cutover

HQ first, in a Saturday 02:00–06:00 window with a rollback snapshot. Spokes on following nights, about 45 minutes each, watched in PRTG.

Stabilisation & handover

One week of parallel PRTG / FortiAnalyzer monitoring, SLA threshold tuning, then runbooks handed to operations.

BGP: prefer ISP-1, BFD for fast detection, redistribute into OSPF

FortiOS 7.4 · FG-SITE-A
config router route-map
    edit "RM-ISP1-IN"
        config rule
            edit 1
                set set-local-preference 200
            next
        end
    next
    edit "RM-ISP2-IN"
        config rule
            edit 1
                set set-local-preference 100
            next
        end
    next
end
config router bgp
    set as 65002
    set router-id 10.2.255.1
    set keepalive-timer 10
    set holdtime-timer 30
    config neighbor
        edit "10.255.1.1"
            set remote-as 65001
            set route-map-in "RM-ISP1-IN"
            set soft-reconfiguration enable
            set bfd enable
        next
        edit "10.255.2.1"
            set remote-as 65001
            set route-map-in "RM-ISP2-IN"
            set soft-reconfiguration enable
            set bfd enable
        next
    end
    config network
        edit 1
            set prefix 10.2.0.0 255.255.0.0
        next
    end
end
config router ospf
    config redistribute "bgp"
        set status enable
        set metric 20
        set metric-type 2
        set routemap "RM-TAG-BGP"
    end
end

local-preference is applied inbound on the spoke, so it only influences the spoke’s own choice of path, which is exactly what we want. The route-map RM-TAG-BGP tags redistributed routes so they are never re-imported (see lessons learned).

Security policy

Policies apply to the SD-WAN zone, not to individual tunnels, so a failover never needs a policy change. Anything not listed is denied by the implicit deny.

Validation & results

Detection time is driven by the probe settings: interval 500 ms × failtime 3 = 1.5 s. The lab measurement matched that figure.

  • Failover: from 3–5 minutes with static routes to about 1.5 s with SLA steering (lab).
  • Visibility: per-application traffic dashboards in FortiManager / FortiAnalyzer, where there were none before.
  • Encryption: all intersite traffic now runs in IPsec tunnels.
  • Cutover: HQ plus three spokes migrated in maintenance windows with no reported production impact.

Lessons learned

ProblemFix
BGP flapping on the 20 Mb/s ISP-2 linksConservative timers (10 s / 30 s) plus BFD at 300 ms for fast detection.
OSPF ↔ BGP redistribution loopTag routes on redistribution and deny that tag on re-import.
FortiManager push failures from config driftRetrieve the device config before every push; resolve conflicts in a staging ADOM.
Active VoIP calls dropped on failoverSIP session helper on both tunnels and a 500 ms probe interval.
Asymmetric routing after cutoverZone-based policy routing keeps each session on one path.
Lab ≠ production (PPPoE on ISP-1)Production-specific FortiManager layer on top of the validated base template.
