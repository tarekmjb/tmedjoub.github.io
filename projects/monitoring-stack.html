Context & objectives

Thresholds and configuration below are representative values from this design, shown for illustration.

In a multisite network, the problem is rarely a lack of alerts. It is too many emails, no owner and no history. The goal was to turn monitoring into an incident workflow: detect, open a ticket, assign, resolve, and close automatically when the problem clears.

Architecture

collectionZabbix + SNMPv3authPriv (SHA / AES) on every network device; agents on servers. Templates per device family.
WAN & cloudPRTGPing, SNMP and HTTP sensors on ISP links, IPsec tunnels and cloud endpoints.
incidentGLPIA webhook creates the ticket via the GLPI REST API, with host, severity and graph link. Recovery adds a follow-up and closes it.
noise controlDependencies & hysteresisIf a site router is down, alerts for everything behind it are suppressed. Recovery thresholds sit below problem thresholds to avoid flapping.

Zabbix trigger expressions (6.x syntax)
# Interface saturation, with hysteresis via recovery expression
avg(/FG-SITE-A/net.if.in[ifHCInOctets.5],10m) > 0.9 * last(/FG-SITE-A/net.if.speed[ifHighSpeed.5])
# recovery:
avg(/FG-SITE-A/net.if.in[ifHCInOctets.5],10m) < 0.75 * last(/FG-SITE-A/net.if.speed[ifHighSpeed.5])

# Device unreachable: 3 consecutive ICMP failures
max(/FG-SITE-A/icmpping,#3) = 0

Item keys are simplified for readability; in practice they come from the vendor templates.

Incident workflow

Detect

Trigger fires in Zabbix (or sensor goes down in PRTG).

Open

Webhook creates a GLPI ticket: category, priority from severity, host, last values and a link to the graph.

Assign & acknowledge

Ticket goes to the network group; acknowledging in Zabbix stops escalation.

Resolve

When the trigger recovers, a follow-up is added and the ticket is solved automatically.

Review

Weekly review of top recurring tickets to fix root causes, not symptoms.
