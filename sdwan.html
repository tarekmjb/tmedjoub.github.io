Architecture

Network Topology

Hub-and-spoke SD-WAN topology. HQ FortiGate acts as the central hub with dual ISP links. Each spoke site maintains two IPsec tunnels to HQ (one per ISP) providing active-active or active-passive WAN redundancy with automatic failover managed by SD-WAN SLA rules.

Methodology

Implementation Steps

01

Audit & Baseline Assessment

Documented existing WAN topology, BGP peering tables, routing policies and inter-site latency baselines. Identified bottlenecks in static route failover and lack of application-aware traffic steering.

02

EVE-NG Lab Validation

Built a full replica of the 4-site topology in EVE-NG with FortiGate VMs. Validated SD-WAN rules, BGP advertisement, OSPF redistribution and failover behavior before any production change.

03

IPsec Tunnel Provisioning

Configured dual IPsec tunnels per spoke (one per ISP) using IKEv2 with AES-256/SHA-256. Set up BGP peering over each tunnel with different administrative distances to control preferred path.

04

SD-WAN Rules & SLA Probes

Defined SD-WAN performance SLA probes (latency, jitter, packet loss thresholds). Created traffic steering rules per application type: VoIP → ISP1, bulk data → ISP2, critical apps → lowest latency link.

05

FortiManager Central Push & Cutover

Pushed final configuration from FortiManager to all spoke devices simultaneously during maintenance window. Ran parallel monitoring on PRTG to validate routing convergence and SLA probe results.

Sites A, B, C migrated on consecutive nights. Each spoke cutover took ~45 minutes: tunnel activation → BGP peering → SD-WAN rule enforcement → PRTG baseline capture. Zero production impact across all sites.

One week of parallel monitoring on PRTG and FortiAnalyzer. Tuned SLA probe thresholds based on real traffic patterns. Delivered runbook, topology diagrams and incident response procedures to operations team.

Routing Design

BGP Architecture

BGP runs over each IPsec tunnel interface — two sessions per spoke (one per ISP path). Different local-preference and weight values enforce preferred/backup path selection. OSPF redistributes BGP learned routes into the LAN for seamless reachability.

Security

Resilience

Failover Scenario — ISP1 Down

When ISP1 fails at a spoke site, the SD-WAN SLA probe detects degradation within 1.5 seconds. BGP session over ISP1 tunnel drops (hold-timer expiry or DPD), and traffic seamlessly shifts to the pre-established ISP2 tunnel. The sequence below was measured during EVE-NG lab testing.

t=0s
ISP1 link fails at spoke
t=0.5s
SLA probe detects packet loss >2%
t=1.0s
SD-WAN marks ISP1 SLA as failed
t=1.5s
Traffic steered to ISP2 tunnel
t=1.5s
Full connectivity restored — ISP2 active

Lessons Learned

Challenges & Solutions

⚠ BGP flapping on low-bandwidth tunnels
Keepalive timers too aggressive on 20Mbps ISP2 links caused false BGP drops. Fixed by tuning keepalive/hold to 10s/30s and adding BFD with minimum 300ms intervals.
⚠ OSPF redistribution loop
BGP routes redistributed into OSPF then re-learned via OSPF created a routing loop. Fixed with route-map tagging on redistribution + deny rule on tag re-import.
⚠ FortiManager push failures on config delta
FortiManager policy push failed when device configs diverged from ADOM baseline. Fixed by running retrieve-config before each push and resolving conflicts in staging ADOM first.
⚠ VoIP quality on SLA failover switch
Active calls dropped during ISP failover due to SIP session not surviving path change. Fixed by enabling SIP session helper on both tunnels and reducing SLA probe interval to 500ms.
⚠ Asymmetric routing after cutover
Return traffic from HQ came back via ISP2 while outbound used ISP1 — causing firewall state mismatch. Fixed with SD-WAN zone-based policy routing ensuring symmetric paths per session.
⚠ EVE-NG to production config delta
Lab used static IPs; production used PPPoE on ISP1. Fixed by adding a production-specific config layer in FortiManager on top of the lab-validated base template.
