Migration SD-WAN d’entreprise

Passage d’une entreprise de quatre sites du MPLS et des routes statiques à un SD-WAN Fortinet en étoile : deux FAI par site, IPsec IKEv2 / AES-256 et BGP/OSPF. Validé sous EVE-NG avant la bascule.

Contexte & objectifs

Les configurations sont anonymisées et simplifiées pour publication. Les temps de bascule sont des mesures de lab réalisées sous EVE-NG avec des VM FortiGate 7.4.

L’entreprise reliait ses sites par un WAN historique : MPLS et routes statiques. En cas de panne, le trafic restait bloqué jusqu’à la modification de la route statique, soit 3 à 5 minutes. Aucune visibilité par application, et une partie du trafic MPLS circulait en clair.

Objectifs

  • Une bascule rapide et automatique entre les liens.
  • Une orientation du trafic par application (VoIP, gros volumes, applications métier).
  • Chiffrer tout le trafic inter-sites, à la place des segments MPLS en clair.
  • Réduire les coûts en envoyant les gros volumes sur un second FAI moins cher.
  • Gestion et journaux centralisés (FortiManager, FortiAnalyzer).

Architecture

Un overlay en étoile : le FortiGate du siège est le hub, chaque agence est un spoke avec deux tunnels IPsec vers le siège, un par FAI. BGP tourne dans chaque tunnel, le routage suit donc l’état des tunnels ; OSPF propage les routes dans chaque LAN.

Choix de conception

pourquoi en étoileInspection centraliséeTout le trafic internet des agences repasse par le siège pour l’IPS et le contrôle applicatif : un seul point de politique, une seule source de logs.
pourquoi BGP sur IPsecRoutage dynamique par tunnelUn tunnel tombé retire ses routes tout seul. Aucune route statique à modifier, et un nouveau site ne demande qu’un voisin de plus.
pourquoi des sondes SLALa performance, pas seulement l’état du lienUn lien peut être actif mais inutilisable. Les sondes mesurent latence, gigue et perte, et orientent chaque application vers le lien qui respecte son SLA.
pourquoi BFDBGP stable sur les petits liensDes timers BGP courts provoquaient des flaps sur les liens 20 Mb/s. BFD détecte vite les pannes, BGP garde des timers prudents de 10 s / 30 s.

Mise en œuvre

Audit & état des lieux

Documentation des peerings, politiques de routage et latences par site. Causes identifiées : bascule par routes statiques et aucune orientation applicative.

Maquette complète sous EVE-NG

Quatre VM FortiGate 7.4 (2 vCPU / 2 Go chacune) sur un hôte de 32 Go. Chaque règle et chaque scénario de panne y a d’abord été testé.

Déploiement IPsec

IKEv2, AES-256 / SHA-256, groupe DH 14 avec PFS, DPD. Deux tunnels route-based par agence, BGP sur chacun.

Règles SD-WAN & sondes SLA

La VoIP préfère ISP-1, les gros volumes passent par ISP-2, les applications métier prennent le membre à plus faible latence.

Déploiement FortiManager & bascule

Le siège d’abord, un samedi entre 02h00 et 06h00 avec un snapshot de retour arrière. Les agences les nuits suivantes, environ 45 minutes chacune, sous surveillance PRTG.

Stabilisation & passation

Une semaine de supervision PRTG / FortiAnalyzer en parallèle, ajustement des seuils SLA, puis remise des procédures à l’exploitation.

Configuration clé

Membres SD-WAN, sonde SLA et règle VoIP (agence)

FortiOS 7.4 · FG-SITE-A
config system sdwan
    set status enable
    config zone
        edit "SDWAN-ZONE"
        next
    end
    config members
        edit 1
            set interface "HQ-ISP1"
            set zone "SDWAN-ZONE"
        next
        edit 2
            set interface "HQ-ISP2"
            set zone "SDWAN-ZONE"
        next
    end
    config health-check
        edit "SLA-VOIP"
            set server "10.1.0.10"
            set interval 500
            set failtime 3
            set recoverytime 5
            set members 1 2
            config sla
                edit 1
                    set latency-threshold 100
                    set jitter-threshold 20
                    set packetloss-threshold 2
                next
            end
        next
    end
    config service
        edit 1
            set name "VoIP-Preferred-ISP1"
            set mode sla
            set dst "VOIP-SERVERS"
            config sla
                edit "SLA-VOIP"
                    set id 1
                next
            end
            set priority-members 1 2
        next
    end
end

BGP : préférer ISP-1, BFD pour la détection rapide, redistribution dans OSPF

FortiOS 7.4 · FG-SITE-A
config router route-map
    edit "RM-ISP1-IN"
        config rule
            edit 1
                set set-local-preference 200
            next
        end
    next
    edit "RM-ISP2-IN"
        config rule
            edit 1
                set set-local-preference 100
            next
        end
    next
end
config router bgp
    set as 65002
    set router-id 10.2.255.1
    set keepalive-timer 10
    set holdtime-timer 30
    config neighbor
        edit "10.255.1.1"
            set remote-as 65001
            set route-map-in "RM-ISP1-IN"
            set soft-reconfiguration enable
            set bfd enable
        next
        edit "10.255.2.1"
            set remote-as 65001
            set route-map-in "RM-ISP2-IN"
            set soft-reconfiguration enable
            set bfd enable
        next
    end
    config network
        edit 1
            set prefix 10.2.0.0 255.255.0.0
        next
    end
end
config router ospf
    config redistribute "bgp"
        set status enable
        set metric 20
        set metric-type 2
        set routemap "RM-TAG-BGP"
    end
end

La local-preference est appliquée en entrée sur l’agence : elle n’influence que le choix de chemin de l’agence, ce qui est exactement l’objectif. La route-map RM-TAG-BGP marque les routes redistribuées pour qu’elles ne soient jamais réimportées (voir retours d’expérience).

Politique de sécurité

Les politiques s’appliquent à la zone SD-WAN et non aux tunnels : une bascule ne nécessite donc aucun changement de politique. Tout ce qui n’est pas listé est bloqué par le refus implicite.

FluxServicesInspectionAction
Site ↔ site (métier)HTTPS, SMB, RDPIPSallow
VoIPSIP, RTPaucune (latence)allow
Siège → InternetanyIPS + contrôle applicatifallow
Agence → Internet (via siège)HTTP, HTTPSIPSallow
Agence → FAI en directany—deny
Inter-sites inconnuany—deny

FortiAnalyzer conserve les journaux de session 90 jours.

Validation & résultats

Le temps de détection découle des réglages de sonde : interval 500 ms × failtime 3 = 1,5 s. La mesure en lab correspond à ce calcul.

  • Bascule : de 3–5 minutes avec les routes statiques à environ 1,5 s avec l’orientation SLA (lab).
  • Visibilité : tableaux de bord par application dans FortiManager / FortiAnalyzer, inexistants auparavant.
  • Chiffrement : tout le trafic inter-sites passe désormais dans des tunnels IPsec.
  • Bascule en production : siège et trois agences migrés en fenêtres de maintenance, sans impact signalé sur la production.

Retours d’expérience

ProblèmeCorrection
Flaps BGP sur les liens ISP-2 à 20 Mb/sTimers prudents (10 s / 30 s) et BFD à 300 ms pour la détection rapide.
Boucle de redistribution OSPF ↔ BGPMarquage des routes à la redistribution et refus de ce tag à la réimportation.
Échecs de push FortiManager dus à la dérive de configRécupérer la config de l’équipement avant chaque push ; résoudre les conflits dans un ADOM de préproduction.
Appels VoIP coupés lors de la basculeSIP session helper sur les deux tunnels et sondes toutes les 500 ms.
Routage asymétrique après la basculeLe routage par zone garde chaque session sur un seul chemin.
Lab ≠ production (PPPoE sur ISP-1)Une couche FortiManager propre à la production, au-dessus du modèle validé.
