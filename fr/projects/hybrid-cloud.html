Architecture cloud hybride

Un FortiGate local relié à Azure VPN Gateway et AWS Transit Gateway en IPsec route-based, avec échange BGP, filtrage strict des préfixes et supervision PRTG centralisée.

Contexte & objectifs

Projet de lab. Adressage, ASN et IP sont des valeurs de lab (plages de documentation pour les IP publiques). Les clés pré-partagées sont masquées.

La plupart des entreprises finissent avec des charges dans plusieurs clouds. L’objectif de ce lab : relier un site local à Azure et AWS en même temps, comme le ferait une entreprise : chiffré, routé dynamiquement, filtré et supervisé depuis un seul endroit.

  • IPsec route-based (IKEv2) d’un FortiGate vers Azure VPN Gateway et AWS Transit Gateway.
  • BGP partout : aucune route statique vers le cloud, les nouveaux VNet / VPC apparaissent automatiquement.
  • Filtrage strict : le site n’annonce que son LAN et n’accepte que les préfixes cloud attendus.
  • Une seule vue de supervision (PRTG) pour les tunnels, les sessions BGP et la latence de bout en bout.

Choix de conception

route-based plutôt que policy-basedTunnels vus comme des interfacesC’est le routage qui décide de ce qui entre dans un tunnel : BGP, SD-WAN et politiques de pare-feu fonctionnent par-dessus.
Transit Gateway plutôt qu’un VGWPasse à l’échelle sur plusieurs VPCUne seule attache VPN sert tous les VPC rattachés au TGW. La propagation remplit automatiquement sa table de routage.
prefix-lists en entrée et en sortieAucune fuite de routesSans filtre, le FortiGate pourrait réannoncer les routes AWS vers Azure et devenir un transit imprévu entre clouds.
Ajustement du MSSPas de pertes silencieusesL’en-tête IPsec réduit la MTU utile. Le MSS TCP est fixé à 1350 sur les politiques vers le cloud pour éviter les problèmes de fragmentation.

Mise en œuvre

Plan d’adressage & ASN

Préfixes sans chevauchement entre site, Azure et AWS ; ASN privés par domaine (65001, 65515, 64512).

Côté Azure

VNet avec GatewaySubnet, VPN Gateway route-based avec BGP, Local Network Gateway décrivant le FortiGate, puis la connexion.

Côté AWS

Transit Gateway, attache VPC, Customer Gateway (IP publique + ASN du FortiGate) et VPN Site-to-Site attaché au TGW : deux tunnels.

Côté FortiGate

Trois interfaces IPsec, trois voisins BGP, prefix-lists, politiques de pare-feu avec ajustement du MSS.

Supervision

Capteurs PRTG pour l’état des tunnels, des sessions BGP et la latence vers une VM de test dans chaque cloud.

Configuration clé

Azure (CLI)

az cli
# Route-based VPN gateway with BGP (ASN 65515)
az network vnet-gateway create -g rg-hybrid -n vgw-hub \
  --vnet vnet-hub --public-ip-addresses pip-vgw \
  --gateway-type Vpn --vpn-type RouteBased --sku VpnGw1 --asn 65515

# The FortiGate, seen from Azure
az network local-gateway create -g rg-hybrid -n lng-onprem \
  --gateway-ip-address 203.0.113.10 --asn 65001 \
  --bgp-peering-address 10.1.255.1 --local-address-prefixes 10.1.255.1/32

az network vpn-connection create -g rg-hybrid -n cn-onprem \
  --vnet-gateway1 vgw-hub --local-gateway2 lng-onprem \
  --shared-key "<redacted>" --enable-bgp

AWS (CLI)

aws cli
aws ec2 create-transit-gateway --options \
  AmazonSideAsn=64512,VpnEcmpSupport=enable,DefaultRouteTablePropagation=enable

aws ec2 create-customer-gateway --type ipsec.1 \
  --public-ip 203.0.113.10 --bgp-asn 65001

aws ec2 create-vpn-connection --type ipsec.1 \
  --customer-gateway-id cgw-0abc --transit-gateway-id tgw-0def \
  --options "TunnelOptions=[{TunnelInsideCidr=169.254.10.0/30},{TunnelInsideCidr=169.254.11.0/30}]"

FortiGate : BGP avec filtrage

FortiOS 7.4 · FG-HQ
config router prefix-list
    edit "PL-ONPREM-OUT"
        config rule
            edit 1
                set prefix 10.1.0.0 255.255.0.0
            next
        end
    next
    edit "PL-AZURE-IN"
        config rule
            edit 1
                set prefix 10.100.0.0 255.255.0.0
                set le 24
            next
        end
    next
    edit "PL-AWS-IN"
        config rule
            edit 1
                set prefix 10.200.0.0 255.255.0.0
                set le 24
            next
        end
    next
end
config router bgp
    set as 65001
    set router-id 10.1.255.1
    set ebgp-multipath enable
    config neighbor
        edit "10.100.255.30"
            set remote-as 65515
            set ebgp-enforce-multihop enable
            set update-source "lo-bgp"
            set prefix-list-in "PL-AZURE-IN"
            set prefix-list-out "PL-ONPREM-OUT"
        next
        edit "169.254.10.1"
            set remote-as 64512
            set prefix-list-in "PL-AWS-IN"
            set prefix-list-out "PL-ONPREM-OUT"
        next
        edit "169.254.11.1"
            set remote-as 64512
            set prefix-list-in "PL-AWS-IN"
            set prefix-list-out "PL-ONPREM-OUT"
        next
    end
    config network
        edit 1
            set prefix 10.1.0.0 255.255.0.0
        next
    end
end

L’adresse BGP d’Azure se trouve dans le GatewaySubnet (ici 10.100.255.30) : le FortiGate la joint à travers le tunnel en eBGP multihop depuis une loopback. Côté AWS, les pairs sont les adresses .1 de chaque /30 interne, et ebgp-multipath permet aux deux tunnels de porter du trafic.

Points d’attention

  • La création d’une Azure VPN Gateway peut prendre plus de 30 minutes : la lancer en premier.
  • Les inside CIDR des tunnels AWS doivent être des /30 de 169.254.0.0/16, hors des plages réservées par AWS.
  • Des préfixes qui se chevauchent entre sites et clouds cassent tout. Planifier l’adressage avant le premier tunnel.
  • Sans prefix-list en entrée, une erreur dans une table de routage cloud peut atteindre votre LAN.
